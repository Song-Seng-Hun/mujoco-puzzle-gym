# Parts and presets

[Back to the guide](guide.en.md)

A puzzle room is assembled from parts. This document covers how parts connect through signals, the steps for building a room from presets, the check and staged training, and the value tables of every part. The value tables are generated by `mpg parts --markdown`; the rest is written by people.

## Parts, presets and assembly presets

- A **part** is one line in `parts:` of `room.yaml`. It is made of a type (`type`) and its values. Each type fixes the values it accepts with their units, defaults and allowed ranges (the value schema); `mpg build` and `mpg check` reject out-of-range values and give the reason and the range.
- A **part preset** is one part type with a set of default values. It has no code. Presets live in `src/mujoco_puzzle_gym/presets/parts/<category>/<name>.yaml`, and the categories are `input` (buttons, sensors), `logic` (gates, counters, transceivers), `device` (doors, warps, goal nets, platforms, pillars, turntables, conveyors, springs, setters), `floor`, `trap`, `object`, `beak` and `npc` (robots that move by themselves).
- An **assembly preset** bundles several parts, or is a whole room. Assembly presets live in `presets/puzzles/<topic>/<name>.yaml`.

`mpg parts --json` lists the registered parts, their value schemas and the presets. To include your own parts, add `--plugin my_parts`.

## Building a room from presets

Write `preset:` on a part line to take the type and values from the preset; values written on that line override the preset's.

```yaml
parts:
  - {name: button_a, preset: input/floor_oneshot, pos: [-0.35, 0.55]}
  - {name: door, preset: device/sliding_door, pos: [0.4, 0.0], width: 0.4, in: [button_a]}
```

Write `preset:` (one name or a list) at the top of the room to lay down an assembly preset and put the room's values on top of it.

```yaml
preset: puzzles/coins/coin_lock     # 3 coins, coin lock lock, door lock_door
size: [2.4, 1.8]
spawn: {pos: [-0.9, -0.7]}
parts:
  - {name: lock, need: 2}                         # same name: change values only
  - {name: goal, type: goal, pos: [0.85, 0.0]}    # new name: add
```

The merge rules are as follows. Merging goes in list order, and the room file comes last.

- Top-level values (`size`, `spawn`, `demo` and so on) are replaced by later ones. A preset's `name` is not inherited.
- `parts` are matched by `name`. If a line with the same name has `type` or `preset`, the whole part is replaced; otherwise only the values written there change. New names are appended.
- `links` are concatenated.

The final values, overrides included, are recorded at training time in `room_parts` of `runs/<id>/task.resolved.yaml`.

Steps for building a room:

1. Pick presets from `mpg parts --markdown` or the tables below.
2. Set the walls and the start point, and write `preset`, `pos` and the values to change on each part line.
3. Connect signals: in the receiving part's `in:`, write the channel name of the sending part.
4. Look at the picture with `mpg build`, and check with `mpg check`.

## Signal bus

Parts send and receive signals through named channels.

- Channel values are real numbers. On and off are 1 and 0, and anything above 0.5 reads as on. A counter carries its count as is.
- A part reads the channels in `in` and writes to the channels in `out`. Without `out`, a signal-emitting part such as a button or gate writes to the channel with its own name. A counter also emits dotted channels such as `<name>.count` and `<name>.reached`.
- When `enable: <channel>` is off, that part's output stops (power).
- Every body step updates input parts → logic parts → device parts once each in that order, so a signal goes from a button to a door within the same step.
- A loop made only of stateless parts (NOT → NOT) is rejected. A loop that includes a stateful part such as a delay or latch is allowed.
- M1's `links: [{from, to}]` is the same as adding the sending part's channel to the receiving part's `in`.

## Expression gate syntax

`type: gate` computes its output with one of the following.

- `expr`: an expression over channels. Examples: `a and not b`, `delay(btn, 1.5)`, `latch(pulse(a), reset_btn)`, `count(lap) >= 3 or timer(plate) > 2`.
- `op` and `in`: a form that does not put channel names in an expression, so presets use it (`logic/and` and others). `and`, `or` and `xor` take all inputs; `not`, `delay`, `hold`, `pulse`, `timer` and `count` take one input; `latch` takes `[set, reset]`.
- `sequence: [a, b, c]`: a sequence lock. When the order is wrong, `<name>.wrong` turns on for one step.
- `logic: <name>`: a Python function registered with `register_logic`.

What expressions can use: channel names (a dotted name like `laps.count` is also one channel), numbers, `and or not xor`, comparisons (`< <= > >= == !=`), parentheses, and the functions `delay(x, s)`, `hold(x, s)`, `pulse(x)`, `latch(set, reset)`, `count(x)` and `timer(x)`. Arithmetic, attribute access, calls to other functions and strings are rejected when the room is loaded. Expressions are parsed with `ast`, checked against an allow list and evaluated by this package itself, so opening a room file someone else made does not run any code.

## Moving devices and setters

- Platform (`platform`, presets `device/moving_platform`, `device/elevator`): follows `path: [[dx, dy, z], ...]`, measured from `pos` (z is the top face height), at `speed`. `mode` is `loop`, `pingpong` or `once`; `run` is `always`, `while_signal` (while the signal is on) or `on_signal` (one trip per turn-on). It moves on slide joints with position actuators, so objects on it ride along.
- Lift pillar (`pillar`), turntable (`turntable`), conveyor (`conveyor`): while the signal is on they rise, spin, or move the body and objects on the belt at belt speed. The conveyor belt is drawn on the floor, so its friction is the floor's.
- Spring (`spring`, preset `device/spring_pad`): gives what is on the pad the velocity `velocity` [vx, vy, vz]. The preset launches objects only (`trigger: object`).
- Setter (`setter`): when the signal turns on it sets `target: <part>.<value>` to `value`; with `revert: true` it puts the old value back when the signal turns off. Only values marked "yes" under "Runtime change" in the tables below can be targets; size values such as a door's width are rejected when the room loads.
- Value binding `bind`: a value every part takes. `bind: {speed: {from: lever.angle, map: [-1, 1, 0, 0.3]}}` maps a channel linearly onto a number value that can change while running, clipped to the value's range every body step. A value changed by both a `bind` and a setter is rejected.
- Solution orders and the solver keep off platform and turntable cells and off pillars that will rise. Whether the body stays up riding them is outside what the walking policy learned, so it is only recorded. Record of 2026-11-12: no fall in 3 s on a platform at 0.1 and 0.3 m/s and on a belt at 0.1 and 0.2 m/s.

## Traps

Traps (the `trap` group) push the body, knock it over or let it fall. Each one acts only while its `in` signal is on (always, without `in`), and one value, `power`, sets its strength. `enabled: 0` turns it off (a pit without `in` is always open and cannot be switched; `enable` or `enabled` on it is rejected, so give it an `in` to switch it). `power` and `enabled` can change while running, so setters, `bind` and difficulty steps (below) tune them.

| Trap | Preset | `power` |
|---|---|---|
| wind `wind` | `trap/crosswind` | force on the body and objects in its zone [N], direction `yaw` |
| pusher `pusher` | `trap/pusher` | speed of the paddle running out of its housing and back [m/s] |
| spinning bar `spinner` | `trap/spinning_bar` | turn rate of a bar at floor height [deg/s] |
| pendulum `pendulum` | `trap/pendulum` | swing amplitude [deg]; `period` sets the period |
| pit `pit` | `trap/pit` | none. Falling in means `on_fall: fail` (the episode fails) or `reset` (back to the start or a checkpoint). With `in`, a lid covers it while off |
| cannon `cannon` | `trap/cannon`, `trap/cannon_turret` | shell launch speed [m/s] |
| slippery and sticky floor | `trap/slippery_floor`, `trap/sticky_floor` | friction of a floor tile (`floor_tile`) |

- The solve order and the solver treat a pit, the sweep of a spinning bar or pendulum, and the reach of a pusher as holes and walk around them.
- A cannon fires `burst` shells every `period` seconds (with `fire: edge`, once per rising edge). `aim` is `fixed` (`yaw` + `aim_yaw`, `aim_pitch`), `at_body` (where the body is now), `lead` (where it is going) or `signal` (`aim_yaw` and `aim_pitch` bound to channels with `bind`). `spread` is the half angle of a cone around the aim. `<name>.fired` is on for one step when it fires; `<name>.hits` counts hits on the body.
- Shells come from a pool of `pool` prebuilt ones (default 10). After `lifetime` seconds, or when all are out, the oldest is taken back and fired again. Snapshots include shells in flight.
- Shells never press buttons, pressure plates or zones; only targets (`input/target`) count them. A target hit at `min_speed` or faster raises `<name>.hits` and turns on (`mode: latch` stays on, `pulse` for one step).
- A turret (`trap/cannon_turret`) aims by a signal such as a lever and fires once when its signal turns on. `mpg check` traces the ballistic path over the whole aim range the `bind` can produce and passes if any aim hits the target board. With `spread`, the whole cone has to land on the board.
- Knockdown record (2026-11-12, standing body, 0.4 m away, from the side and the front, 3 shots each): shell mass × speed of 0.5 N·s or less never knocked it over; falls started at 0.6 N·s (0.1 kg, 6 m/s, front); at 0.8 N·s (0.2 kg, 4 m/s) 4 of 6 fell and at 1.0 N·s (0.2 kg, 5 m/s) all 6. The default is therefore 0.2 kg at 5 m/s. A walking body is weaker: with 0.4 N·s shells every 2.5 s, the solver fell in 6 of 20 runs.
- Shell mass (`shell_mass`) is fixed when the room is built. MuJoCo precomputes the mass matrix of a free body, so changing the mass while running gives wrong motion.

## NPC robots

The `npc` category is a small robot that slides over the floor by itself (`type: npc`). It moves on three planar joints (x and y slides, a z hinge) with velocity actuators, and it has mass, so it collides with the body, objects and walls. Floor buttons and zones see the robot's centre like an object's (`trigger: npc` or `any`). It has no vertical joint and so puts no weight on the floor; a pressure plate counts the robot's `mass` while its centre is over the plate. It carries a marker on top.

| `behavior` | Preset | What it does |
|---|---|---|
| `flee` | `npc/flee` | Runs the other way when the body comes within `sense`. When blocked it slides along the wall |
| `follow` | `npc/follow` | Comes towards the body within `sense` and stops `keep` away |
| `lure` | `npc/lure` | Comes towards the `bait` object (a cube) while the body holds it, stopping `keep` short |
| `patrol` | `npc/patrol` | Drives round `path` (points measured from `pos`, a loop). Stops and waits while the body blocks the way |
| `guard` | `npc/guard` | Keeps its post (`pos`); when the body comes within `sense + reach` it steps out up to `reach` to block it |
| `shy_gaze` | `npc/shy_gaze` | Freezes while the body looks at its marker (gaze sensor, room `gaze:`) and creeps towards the body otherwise. `invert: true` swaps this |
| `seek_button` | `npc/seek_button` | When `in` turns on it drives onto the `button` part and stays there |
| `sleepy` | `npc/sleepy` | Drives round `path` for `awake` seconds, then stands still for `asleep` seconds, again and again |

- Common values: `speed` (top speed, default 0.08 m/s), `accel`, `sense` (detection radius), `size`, `mass`, `leash: [x0, y0, x1, y1]` (a box in room coordinates the robot's centre never leaves). With `enable` off it stops where it is. `speed`, `accel`, `sense`, `keep`, `reach`, `awake` and `asleep` can change at run time.
- Avoiding walls: it casts five rays, along the way it wants to go and at ±35° and ±70° from it, and takes the first clear one. With all five blocked it stops. The rules use no random numbers, so one seed gives one trajectory.
- Channels: `<name>.moving` (1 while it moves), `<name>.on` (marker id of the button it stands on, -1 for none). The observation item `npcs` gives each robot's relative position, velocity, whether it moves and whether it is reacting (6 numbers).
- A `speed` at or above the body's walking speed (about 0.16 m/s) is a warning in the `parts` stage of `mpg check` (not a failure): the body could not catch it.
- A `seek_button` robot's `button` (a button, zone, laser or pressure plate the robot can set off) counts as on in the solution order once the robot's `in` are on (with no `in`, from the start). The body is not sent onto it; the robot drives there and presses it. So a room "switch A -> robot (`in: [A]`) -> plate -> door" is solved by pressing A.
- Any other input only robots set off (`trigger: npc`, no `objects` list) counts as a switch in the solution order when it lies inside the `leash` of a robot that can be herded (`flee`, `follow`, `lure` with a cube bait; with no `leash`, anywhere). Write `herd <robot> <part>` (or `herd <robot> <x> <y>`) in the solution's `demo:`: a `flee` robot is driven from its far side, a `follow` robot is led. For a `lure` robot, first `grab <bait>`, then `herd` leads it with the held bait.

## Two-phase check

`mpg check room.yaml` is split into a static phase (no simulation) and a dynamic phase. `static.failed` and `dynamic.failed` in the result list the failed stages in order.

Static phase:

| Stage | What it checks |
|---|---|
| `values` | Values within the schema ranges, preset names that exist, marker ids |
| `channels` | Reading a channel nobody writes, two parts writing one channel, stateless loops, links to missing parts |
| `demo` | Commands and targets of the `demo:` subgoals |
| `body` | Whether the body has the `requires_body` capabilities of the parts |
| `parts` | Per-part checks (a ball larger than the goal-net mouth, balls or coins that cannot be reached). An NPC robot as fast as the body is only a warning (`warnings`), not a failure |
| `overlap` | Whether a part's solid body sinks more than 5 mm into a wall or another part in the default layout. Floor pads, flags and goal zones are skipped, and a door may overlap only its own walls (the walls of the gap it closes, and walls on the same line) |
| `order` | Whether the signals and walls allow a solution order that reaches the goal. For text-map rooms, also whether parts sit on floor cells, and blocking ledges and slopes |
| `actions` | Whether the task `actions` have what the solution needs: `grab` when an object must be carried or a handle device worked (`grab` or `pull` in `demo:`, an input in the solution order only a grabbable object can set off, or a handle device in the solution order), `head` when a wall button the solution presses has its top edge below the level beak tip (0.21 m) |

The first three stages (`values`, `channels`, `demo`) fail while the room is being loaded, so in that case the result has only the failed stage and the solver stage is skipped. To run only the static phase, add `--static`.

Dynamic phase:

| Stage | What it checks |
|---|---|
| `stability` | That the body does not fall or blow up numerically for 10 s at zero command |
| `solver` | That a scripted solver that knows the answer solves at least 18 of 20 random layouts. If the room has `demo:` (`goto`, `press`, `wait`, `push <ball> to <goal_net>`, `herd <robot> <part>`, `turn <lever or dial> <value>`, `pull <cord or drawer>`, `look <part>`, `take <dispenser>`), the solver follows that order first, and a grid solver takes over for the rest |

The solver stage saves a snapshot for each flag it passes in `runs/check/<room>/checkpoints/<flag>.pkl`.

## Checkpoints and staged training

A room with flags (`input/checkpoint_flag`, `order: 1, 2, …`) is split into segments. First make the flag snapshots with `mpg check`, then open the segments one by one with `mpg train --curriculum forward`. Details are in [staged training in the guide](guide.en.md#staged-training-and-segment-evaluation).

```bash
mpg check examples/rooms/four_flags.yaml
mpg train task.yaml --minutes 60 --curriculum forward
mpg eval runs/<id> --full --segments
```

### Difficulty steps

`difficulty:` in `task.yaml` raises values such as trap strength in steps. Only values that may change while running ("yes") or at episode start can be stepped.

```yaml
difficulty:
  - {param: cannon_a.power, from: 2.0, to: 5.0, steps: 4}   # 2, 3, 4, 5 at steps 0..3
  - {param: wind_a.enabled, from: 0, to: 1, at_step: 2}      # on from step 2
curriculum: {mode: forward, order: difficulty_first}
```

- `steps: n` splits `from`..`to` into n steps; `at_step: k` uses `to` from step k on. When rows have different step counts, the longest wins and shorter rows stay at their last value.
- Staged training opens (segment, difficulty) pairs one at a time. `order: difficulty_first` (the default) raises every step of a segment before the next segment; `segment_first` opens every segment at one step before the next step. Level names are `<segment>@d<step>`, recorded in `curriculum.json` and the episode log.
- Values driven by `bind`, values out of range and size values are rejected when the room loads.
- Without a draw (evaluation, a plain `reset`) the last step is used. `mpg eval runs/<id> --difficulty 1` picks a step.

## Cubes and beak grabbing

- `cube` is a box with handles (`size`, `mass`, `friction`, handle faces `handles` from `+x`, `-x`, `+y`, `-y`, `+z`; default the four sides). Pressure plates, sockets, object buttons and zones count it. When a room has a cube, inputs a cube can set off count as switches in the solution order.
- Beak grabbing is a simulation simplification that does not carry over to the real duck. The simulated model has no beak joint, so when the beak tip (`mouth_tip`) is within `grab_radius` (default 4 cm) of a handle and the grab command goes above 0.5, a weld constraint between the head and the cube switches on. The head and the cube do not collide. At 0.5 or below it lets go. A cube heavier than the body's `max_lift_mass` (default 0.05 kg) is not grabbed and `beak.too_heavy` is 1. If holding takes more than `max_hold_force`, the cube is dropped and `<cube>.dropped` pulses; grabbing again needs the command to go down and up once.
- The beak tip is 0.135–0.21 m above the floor, so a cube on the floor is out of reach. A cube on the front edge of a 0.17–0.19 m stand, handle towards the body, can be grabbed by walking into it. In a letter map a raised floor cell (`legend` `{type: floor, height: 0.18}`) is such a stand.
- Channels: `beak.holding`, `beak.held_id` (marker id of the held object, -1: none), `beak.too_heavy`, and per grabbable object `<object>.held`, `<object>.dropped`. Floor buttons, pressure plates, zones and sockets do not count a held object. Snapshots restore the hold too. A warp takes a held object along, keeping its pose to the head.
- Obs item `beak`: holding, held object kind (cube 1, none 0, other objects in the next section), and the nearest handle relative to the beak tip (x, y, z in the heading frame). 5 values.
- Wall buttons: `mount: wall` on a `button` makes a plate (`size`: [width, height]) on the wall face at `pos`, centred `height` up, facing `facing`. It is pressed while the beak tip is over the plate and within 6 cm in front of its face (with the head lowered against a wall the chest meets the wall first and the tip stays 4–5 cm off). Behind the face it counts only up to the plate thickness + 1 cm, so a duck on the far side of a thin wall cannot press it. `trigger` does not apply.
- Upper-level actions: `task.yaml` `actions: [move]` (default) can add `head` (lower the head, 1 value: -1 level, 1 lowest) and `grab` (1 value, above 0.5 grabs), in that order. The action size is 3 plus those added. The scripted solver does only what a policy can: a room that needs a cube carried or a low wall button pressed fails the `mpg check` stage `actions` when the task has no `grab` / `head`. Example: `mpg check examples/rooms/cube_plate.yaml --task examples/task_cube_plate.yaml`.
- Solution `demo:`: `grab <object>` (walk up to a handle, match the head height, grab), `place <object> <part>` (carry it over the part's centre, stop, let go, step away). Wall buttons are pressed with the head lowered, by `press <button>` or in the solution order.
- Example [`examples/rooms/cube_plate.yaml`](../examples/rooms/cube_plate.yaml): pick the cube off its stand and put it on the pressure plate to open the door.

## Beak objects and receivers

Every object with handles is grabbed the same way as `cube` (same grab radius, liftable mass, drop force, and `.held` / `.dropped` channels). The presets are in the `beak` category.

| Preset | Type | Defaults | Use |
|---|---|---|---|
| `beak/cube_weight` | `cube` | 4 cm, 40 g | A weight for scales and pressure plates, just under the body's `max_lift_mass` (0.05 kg) |
| `beak/laundry` | `laundry` | 12 × 10 cm, 6 mm thick, 20 g, a hem (`hem`) on top of each edge | A light cloth. The plate is rigid; the wrinkles are only its look. Grabbed by a top hem |
| `beak/key` | `key` | 20 g, head 4 cm, shaft 5 cm, a ring at the `-x` end | Carries a marker on its head. Only a receiver with `accept: [<marker id>]` takes it |
| `beak/handle_ball` | `handle_ball` | radius 3 cm, 30 g, a ring on the `-x` side | Rolls once let go. Not the ball part `ball` |
| `beak/egg` | `egg` | 25 g, radius 2.2 cm, height 6 cm, four side knobs, `break_height` 0.05 m, `on_break: fail` | `<egg>.broken` goes to 1 when it breaks. The beak tip is 13.5 cm above the floor, so letting it go on the floor or into a basket breaks it; to deliver it whole, hang it on a hook or set it on a raised stand |
| `beak/stick` | `stick` | 20 cm long, 1.6 cm thick, 20 g, a handle at the `-x` end | Held, its far end presses wall buttons |
| `beak/hook` | `receptacle` `shape: hook` | an 8 × 8 cm post with a 6 cm peg at 0.19 m, `tolerance` 0.04 m | An object let go within 4 cm of the peg tip hangs there |
| `beak/basket` | `receptacle` `shape: box` | 30 × 30 cm, 10 cm walls, `require: count`, `count: 1` | `<basket>.count` and `<basket>.mass` (kg) tell what is in it |
| `beak/scale` | `pressure` `trigger: object` | 20 × 20 cm, `min_mass` 5 g | Number channel `<scale>.mass` (kg, 1 g steps); `<scale>` is 1 from 5 g |
| `beak/wall_button_beak_low` | `button` `mount: wall` | plate 12 × 6 cm centred 0.15 m up, `oneshot` | Reached only with the head lowered (`head` action) |
| `beak/wall_button_beak_mid` | `button` `mount: wall` | plate 12 × 6 cm centred 0.2 m up, `oneshot` | The level beak tip (0.21 m) reaches it standing |

- Egg: it breaks when a contact starts with a relative normal speed at or above that of a drop from `break_height` (√(2·9.81·`break_height`), 0.99 m/s by default). Measured with the default body (2026-11-12): let go from the beak onto the floor, 1.42 m/s (head lowest) to 1.86 m/s (head level); picked off the stand and put on a floor plate, 1.68–1.87 m/s; bumps while grabbing and carrying, 0.24 m/s or less (0.49 m/s pushed into the stand); knocks after landing, 0.35 m/s or less. So at 5 cm only a let-go breaks it. The part default `on_break` is `none` (channel only); the preset uses `fail` (a broken egg fails the episode). A broken egg changes colour; snapshots and reset restore it.
- Key and socket: a receiver's `accept` takes marker ids (integers) besides names and kinds. The socket may carry a marker with the same id; only then may marker ids repeat (other repeats are still rejected). The socket's `angle_tolerance` checks the heading.
- Hook: when a handle of an object that is not held comes within `tolerance` of the peg tip, the object is fixed to the hook and counts as in. Grabbing it again takes it off. The peg is a logical catch you can see but not hit (only the post collides; contacts between the post and grabbable objects are off). `facing` is where the peg points.
- Basket: walls lower than 10 cm trip the body or let it climb over (3 falls in 4 at 5 cm). Over a 10 cm wall the level beak tip reaches 5.8–6.8 cm past the wall face.
- Stick: the far end of a held stick counts at a wall button in the same window as the beak tip (6 cm in front of the plate, plate thickness + 1 cm behind it, within the plate width and height). Measured: a slow scripted approach pressed 10 times in 10 with the end 2.9–5.9 cm in front of the plate face and within 2.7 cm of its height, with a weld force of 0.89 N or less before the press. Walking straight into the wall drops the stick in 4 runs of 6 (the force goes over `max_hold_force`, 3 N). Lowering the head swings the stick end down a lot (about 0.43 rad per head unit).
- Object kind in the `beak` obs: `cube` 1, `laundry` 2, `key` 3, `handle_ball` 4, `egg` 5, `stick` 6, none 0.
- Solution `demo:` adds `drop <object> <part>`: carried as `place`, but let go with the head level (the egg-breaking solution). `place <object> <hook>` brings the leading handle to the peg tip. `press <button>` while holding a stick brings the stick end to the plate height.
- Known limits: receivers count a broken egg too. Scripted solutions that put an object in a basket or on a scale succeed 8–10 times in 10, depending on the room and seed.

## Devices the beak works

A device stands in place and the body works it from its `facing` side (deg). All are switches in the solution order, and their target area is the spot where the body stands to work them. Devices worked by a handle are held by the beak weld at a small knob body on a ball joint (grab radius, letting-go force and the `.held` and `.dropped` channels are the same as for objects).

| Preset | Kind | Defaults | Use |
|---|---|---|---|
| `beak/lever` | `lever` `mode: push` | 3 cells (-1, 0, 1), up to 35°, starts at -1, paddle 7–12 cm up | The body pushes the paddle over with its chest. `<lever>.angle` gives the cell value |
| `beak/pull_cord` | `pull_cord` | cord hung from 0.45 m, knob at 0.19 m, on after a 6 cm pull, `latch` | Hold the knob, turn round and walk away: the cord is drawn out |
| `beak/dial` | `dial` | 4 spokes (cells 0–3), spokes 7–12 cm up, radius 0.15 m, starts at 0, `target: [1, 1]` | Walking past on the line 0.10 m beside the axis turns it one cell |
| `beak/drawer` | `drawer` | tray floor at 0.17 m, slides out 0.15 m, 0.1 m strap, knob at 0.19 m | Hold the strap's knob and turn clockwise in place: it opens and latches open |

- Lever: `detents` is the number of cells (default 3; 0 is continuous, 1 is rejected). A joint spring pulls the arm to the nearest cell (`detent` N·m), and the channel gives only that cell's value. `mode: push` is a floor lever the body pushes from -1 toward 1 by walking forward from the `facing` side. The feet pass under the paddle (7 cm). `mode: grab` is a lever whose knob sits on top of an arm standing toward the body; the body holds it and steps sideways. Because of the measurements, its default `max_angle` is 10°, and the scripted solver does not turn it (below).
- Pull cord: the cord is a 1D flexcomp, weightless through gravity compensation. Its top end hangs from a spring slider inside the arm, so pulling draws cord out, and `<cord>` turns on once `distance` is out. With `latch` it stays on until reset. The cord spring `stiffness` defaults to 2 N/m.
- How to pull: hold the knob, turn clockwise in place until the back faces the device, then walk forward. The default body cannot walk backwards and barely turns counter-clockwise in place.

```text
  Seen from above (the facing side is down)

   [post]─arm─o cord        1. stand at the knob and hold it
               │
               ●  knob      2. turn clockwise while holding
               ▲
              duck          3. walk forward: the cord is drawn out → on
```

- Measured (2026-11-12, default body, `max_hold_force` 3 N): holding a grab lever's knob and stepping to the body's right turned it 9.5–15.7° before the weld force passed 3 N and let go; stepping left, the body did not move (0.2° or less in 12 s). Without a grab, the same sidestep covers 0.19–0.25 m in 4 s. The push lever went over to 1 in 3.2–4.3 s, 5 of 5 without a fall. With the cord, turning while holding the knob took 4.5–5 s, and the solver had it on after 9–11 s in all (at a 4 N/m spring the walk stalls at 3.5–3.7 cm and it never turns on).
- Dial: a floor dial on an upright axis; its spokes are not handles. Walking forward along the line 0.10 m from the axis on the `facing` side, with the axis on the body's left, the chest pushes one spoke round one cell (90° with 4 spokes). It turns one way only (counter-clockwise seen from above). For the next cell the body loops round clockwise (walking, never backwards) and passes on the same side again, so leave about 1 m clear on the `facing` side. `<dial>.angle` is the cell number (0–3) and can aim a turret (aimed per cell); `<dial>` is 1 while the cell is in `target`.
- Drawer: a tray at stand height (0.17 m) in a cabinet; a weightless strap (1D flexcomp) on its front ends in the knob. Hold the knob and turn clockwise in place: the tray is drawn out, and once nearly all the way out (97%) it latches open and `<drawer>` is 1. From then on the strap's knob cannot be grabbed (a held one is let go). Objects placed in the closed tray (up to 0.09 m in from its front) rest on its floor, ride out with it and can be grabbed with the beak; deeper ones fail the `parts` stage of `mpg check`. `pos` is the cabinet's front face and `facing` the side it opens to.
- Dial and drawer measurements (2026-11-12): passing 0.10 m beside the axis turned the dial exactly 90° 10 of 10 times at both vx 0.25 and 0.4; at 0.12 m 10 and 9 of 10, at 0.14 m 5 of 10; no falls. Setting cell 3: 10/10 (about 11 s per loop, about 33 s in all). With the 0.1 m strap and the knob grabbed off-centre (±2.5 cm, ±0.15 rad), the drawer opened and latched 10 of 10 times in 4.8–14.1 s, weld force 0.38 N or less, no drops; a 6 cm strap managed 6 of 10 under the same conditions. The solver (`pull`, then `grab`) opened it and grabbed the cube inside 10 of 10 times (a cube 0.08 m in from the front; one 0.12 m in was out of reach).
- Object kind in the `beak` observation: `lever` 7, `pull_cord` 8, `drawer` 9.
- Solution `demo:`: `turn <lever> <value>` (push levers only, and the value must be one of its cells; the body walks up, pushes, then stops, turns and walks off), `turn <dial> <cell>` (passes and clockwise loops until it is at that cell), `pull <cord or drawer>` (lets go once the cord is on or the drawer latched; holding 6 s without drawing 1 cm more, it lets go and comes again), `look <part>` (when some part reads `<part>.seen`; the body centres that part in view and stands). The grid solver also pushes a lever to 1, turns a dial to its first target cell, pulls a cord and opens a drawer when one comes next in the solution order. With a pull cord or a drawer the task `actions` need `grab`.
- Turrets and levers: when a turret reads a lever's `.angle` through `bind`, `mpg check`'s ballistic check aims once per lever cell instead of over a continuous range. In a room with a turret that aims by a signal and fires when its signal turns on, the target board (`input/target`) becomes a switch in the solution order, and its target area (and the `target_pos` observation) is the spot of the part that fires the turret. A lever or dial whose `.angle` only `bind`s read is a setting knob, not a switch: pushing it to 1 pays no `new_on` and the grid solver does not push it (aim with `turn` in `demo:`).
- Example [`examples/rooms/turret.yaml`](../examples/rooms/turret.yaml): push the lever over one cell to aim the turret at the target, step on the pad to fire, and the door opens.
- Known limits: the scripted solver does not turn grab levers (`turn` rejects them). A push lever is pushed one way (-1 → 1) by default; turning it back (1 → -1) pushes from the other side. A dial turns one way only, so its cell cycles through 0–3, and each further cell takes about 11 s. The static check does not look at the dial's return loop (about 1 m on the `facing` side). Opening a drawer takes 4.8–14 s, and an opened drawer stays open until reset.

## Dispenser

A `dispenser` is a cabinet that hands out one item each time its signal turns on. `pos` is the cabinet front, `facing` (deg) the side the body stands on, and the top `height` (default 0.17 m) is a stand height the beak reaches.

| Preset | Type | Defaults | Use |
|---|---|---|---|
| `beak/dispenser` | `dispenser` `button: floor` | 5 × `beak/cube_weight`, `max_active` 1, `cooldown` 1 s, a 20 × 20 cm floor plate 0.35 m in front | Step on the plate and a weight appears on the top front edge |
| `beak/dispenser_wall` | `dispenser` `button: wall_beak` | Same item and stock, a 10 × 5 cm plate on the front at 0.14 m | Press the plate with the beak, head lowered (`head` action) |

- Why `beak/cube_weight` by default: it has a handle on each of its four sides, so it can be grabbed from any side; 40 g is within the body's `max_lift_mass` (0.05 kg); and the top height matches the measurement that the beak only reaches objects on 0.17–0.19 m stands.
- Trigger (`button`): `floor` is a floor plate at `button_at` ([out, left] m, default [0.35, 0]), `wall_beak` a wall plate on the front at `button_height` (R4 window, 6 cm in front of the plate), `none` the `in` channels. With a plate, `in` channels count too.
- Item (`item`): a grabbable object preset (R28) or NPC preset (R29) by name, or `{preset: <name>, <value>: ...}` with values to override. Other types are rejected when the room loads.
- `stock` (at most 20): copies built up front. `max_active`: copies out at once at most. `cooldown`: wait before the next one. `refill` (a channel): each time it turns on, every stored copy goes back in stock. Exit `exit` ([out, left] m; default objects 2 cm behind the top front edge, robots on the floor 0.15 m in front) and initial velocity `exit_vel` ([out, left, up] m/s, to roll it out).
- Channels: `<dispenser>.stock` (copies left), `<dispenser>.empty` (1 when none). Copies are parts `<dispenser>/<i>`, with `.held` / `.dropped` channels under that name. Copies from one dispenser share one marker id.
- Storage: MuJoCo cannot add bodies while running, so copies are built up front. A stored object waits 5 m below the floor with collisions off and gravity compensated; a stored robot waits at floor height 100 m outside the room with its motors off. Stored copies are left out of observations (`part_pos`, `part_state`, `npcs`, `beak`), beak grabbing, sight (`.seen`), sensors and the solvers. Snapshots and reset restore stock and positions (reset fills the stock).
- Consuming (`consume`): a receiver (`receptacle`, e.g. `beak/basket`) with `consume: true` (default false) makes an accepted object vanish; it still counts (`.count`, `.mass`). A vanished copy no longer counts as out, and with `recycle: true` on its dispenser it is back in stock (otherwise stored until `refill`). A copy that falls through a pit or off a cliff goes back the same way.
- Solution `demo:`: `take <dispenser>` (step on the plate or press it to get one, then stand until it rests). After that, `grab <dispenser>`, `place <dispenser> <part>` and `drop <dispenser> <part>` work on the copy handed out last. The grid solver takes a copy from a dispenser when a receiver in the solution order has nothing it accepts left in the room. A room that takes from a wall-plate dispenser needs `head` in the task `actions`; one that carries objects needs `grab`.
- Measured (2026-11-12, 10 seeds, basket with `consume: true`): `demo: [take d, grab d, place d bk]` 10/10 with the floor plate (10.0–12.6 s) and 10/10 with the wall plate (21.2–25.4 s). The grid solver puts the copy in the basket 9/10 for both presets.
- Known limits: putting it in a basket succeeds 6–10 times in 10 depending on where the basket stands (caught on its edge, or a fall leaning on the basket wall, as in E3b-1). After the grid solver fills a basket, the walk to the next target often gets stuck or falls beside the basket (only 1 in 10 reaches the goal). The scripted solver does not use dispensers that hand out robots.

## Python plugins

A new part inherits `Part` and is registered with `register_part`. Write its values in `fields` as `Field`s, and range checks and the `mpg parts` table come with them. A gate function is registered with `register_logic` and called from a room as `logic: <name>`.

```python
# my_parts.py
from mujoco_puzzle_gym.parts.base import Part
from mujoco_puzzle_gym.registry import register_logic, register_part
from mujoco_puzzle_gym.schema import Field

@register_part("timed_switch")
class TimedSwitch(Part):
    role = "switch"
    stage = "input"
    emits = True
    fields = (Field("seconds", "float", 2.0, unit="s", min=0.1, max=60.0),)
    ...

@register_logic("majority")
def majority(inputs, state, dt):
    return float(sum(v > 0.5 for v in inputs.values()) * 2 > len(inputs))
```

Put `plugins: [my_parts]` in `task.yaml` and this module is imported first, training worker processes included. Preset folders exist only inside this package. Write the default values of your own parts as values in the room file.
