# 体と部品 (R46)

この文書は、**部品が体に何を求めると宣言したか**と、**その宣言が実際に正しいのか**を記録します。
`mpg check`の`body`段階が読むのはまさにこの宣言(`requires_body`)で、下の表の二列目がコードと
食い違えば`tests/test_capability_gate.py`が失敗します。

なぜ別の文書が必要なのか: M2まで、このリポジトリには体が一つしかありませんでした。だから
`Capabilities.missing()`は**つねに空のリストを返し**、どの部品の`requires_body`も一度も反証された
ことのない主張でした。アダプターが一つだけの抽象化は、抽象化ではなく推測です。二つめの体を
つないだら、宣言が嘘だった箇所が四つ出てきました(§4)。

## 1. 体が宣言するもの

| | `microduck` | `go2` |
|---|---|---|
| 能力の名前 | `walk`, `grab`, `roller`, `tow`, `chest_push` | `walk` |
| `max_lift_mass` [kg] | 0.05 | 0.0 (持ち上げるものが無い) |
| `max_step` [m] | 0.01 | 0.03 |
| `max_slope` [deg] | 5.0 | 6.0 |
| `reach_height` [m] | 0.21 | 宣言なし |
| `walk_speed` [m/s] | 0.16 | 1.0 |
| 全体の質量 [kg] | 0.737 | 15.206 |
| `footprint_radius` [m] | 0.11 | 0.41 |
| `fall_height` [m] | 0.07 | 0.15 |

数値の出どころ: `max_step`・`max_slope`・`walk_speed`は、測定の条件(シードの数、指令、合格の基準)が
それぞれの体のアダプターのコメントに書かれています。質量はモデルから読んだ値
(`BodyAdapter.total_mass`)で、`footprint_radius`は体を円で包んだときの半径です — 長い側を覆う
必要があるので、横に通り抜ける幅については保守的です(§6)。

**宣言していない数値の限界は0として読みます**(`bodies.declared_limit`、R45)。分からない限界を
無限として読むほうが危険な方向です。そうすると、体が越えられない部屋を`mpg check`が解けると
言ってしまいます。

### 名前は解剖学を持ち込まない (R67, 2026-11-17)

`beak_grab` と `beak_height` は **`grab` と `reach_height`** になりました。最初の体がくちばし
を持っていたために、ジョーも手も29軸のヒューマノイドも「くちばしで掴む」と宣言する必要があり
ました。これは最初の体の解剖学が共通語彙へ漏れたもので、R2 が防ごうとしている漏れと同じ種類
です。**古い名前はそのまま動きます**（`bodies/base.py` の `ALIASES`）。要求する名前と宣言された
値のキーは比較前に正規化されるので、古い語彙で書かれた部屋・プリセット・プラグイン部品はその
まま動作します。拒否メッセージは呼び出し側が書いた名前を返します。それが各自のファイルで探せる
文字列だからです。

さらに、**どの部品も要求しない能力名はテストが拒否します**
（`tests/test_capability_names.py`）。ゲートは名前だけを比較するため、要求されない名前は拒否も
許可もできず、環境が守らない約束として読まれます。アームが宣言していた `reach`・`gripper` は
要求する部品が0個で、削除しました。その二つが担うはずだった次元はすでに数値で比較されています
（高さは `reach_height`、質量は `max_lift_mass`）。M4 が `two_hands` を作らなかった根拠は同じ
でしたが、同じ PR でアームには適用されていませんでした。だからこれは規則ではなくテストです。

## 4. 宣言が嘘だった四箇所 (2026-11-16の監査)

四箇所とも、修正前はGo2で`check_body`・`check_parts`が**すべて`ok=True`**で、部屋は解けませんでした。

| 部品 | 前 | 後 | 証拠 |
|---|---|---|---|
| `lever` `mode: push` | `[]` | `walk`, `chest_push` | Go2は5シードすべて`.angle`が開始値の-1.000のまま、パドル・ロッドの接触は0回。胴体の下面0.237–0.243 mがパドル上面0.120 mの上を通り、足はパドルの半幅0.060 mの外(\|y\| 0.07–0.14 m)を通ります。**難しいのではなく、当たりません。** マイクロダックは同じ部屋で5/5、1.000まで押しました |
| `dial` | `[]` | `walk`, `chest_push` | 文書に書かれた通過線(軸から0.10 m)でGo2は5シードで+1.16、−0.32、0.00、−0.04、0.00目盛り — 一目盛りを越えたのは1/5で、**2/5はスポークに引っかかって転びました**(胴体のz 0.057)。0.12 mでは0、+2.07、+2.00、+1.00、0目盛り。何も起きないはずの逆方向の通過が+2.0–+5.1目盛り回しました。すね・もも・尻・胴体が一度にスポークを叩きます。マイクロダックはちょうど+1.000(90.0°)で5/5 |
| `hitch_station` | `[]` | `walk`, `tow` | ロープ + attachステーションの部屋がGo2ですべての段階を通るのに、ロープのhitchの一覧が`['sled','post']`で**`body`がありません**。足場を踏んでも永遠に結ばれません。ステーションの存在理由は体のロープの端なのに、それを宣言していませんでした |
| `breakable` `by: [peck]` | `[]` | `grab` | `by: [peck]`の壁のワイヤーの部屋がGo2で通るのに、`World.beak_site`が−1です。永遠に壊れません |

もう一つ、`low_bar`は`[]`→`roller`に変えました。嘘とは別の種類です。`bottom`がスキーマで
0.21–0.246 mに縛られているので、**どんな部屋の設定でも**より大きな体は通れません(Go2の胴体の
上面は0.41 m)。塞がれるのは正しいのですが、理由を述べずに塞がれていました。これからは
`mpg check`が部品の名前を述べて拒否します。

逆に**もともと正直だった箇所**: `rope`を`a: body`で使うと、読み込みのときに
`a: 'body': this body has no tow hitch`で派手に落ちます。黙って通り過ぎることはありません。

## 5. 数値が体に合っていない箇所

部品の力・質量・速度の数値は、一つの体に合わせて測った値です。20倍重い体では意味が変わります。
**既存の数値は変えていません** — 変えれば既存の部屋と測定の記録がすべて揺らぎます。代わりに、
その体で数値が無意味になるときに`mpg check`の`parts`段階が**述べる**ようにしました(失敗ではなく警告)。

| 部品 | 何が食い違うのか | 取った一つの対応 |
|---|---|---|
| `wind` | 力 [N]を加えます。プリセットの1.0 Nは軽い体の重さの14 %、20倍重い体の0.7 %です。スキーマの上限20 Nもその体には重さの13 %なので、測定上で体を倒す区間(28 %)に**合法的に到達できません** | 体の重さの5 %未満なら警告。境界は測定表から持ってきました: 0.5 N(重さの7 %)は20/20通過、1.0 N(14 %)は8/20が転倒、2 N(28 %)は10/10 |
| `pressure`の`trigger`が体を数える場合 | 二つのことが同時に間違っています。(1) 板が体の足跡より狭いと足が一、二本しか乗らず、`.mass`が一歩ごとに揺れます — 既定の0.25 mの板でGo2は平均2.2–5.2 kg、最大9.2 kg、1–5 %のステップで**0 kg**を読み、`min_mass`の0.1・1.0・5.0がすべてどこかのステップでは点いたのに、3 sの終わりには5シードのうち2–3個しか点いていませんでした。0.9 mに広げれば四本の足がすべて乗り、実際の値13.7 kgを読みます。マイクロダック(足跡0.11 m)は既定の板で0.730–0.751 kg、0を読んだことはありません。(2) しきい値が体そのものの質量より低いと、乗るだけで点きます | 両方とも警告。板が足跡の直径より狭いとき、`min_mass`が体の質量以下のとき |
| `npc`の速度 | 警告が`DUCK_SPEED = 0.16`をハードコードして比べていました。測定: 最大の指令でマイクロダックは0.220 m/s、Go2は1.019 m/s(4.6倍)。Go2が簡単に捕まえる0.5 m/sのロボットを「捕まえられない」と警告していました | 体の`walk_speed`能力の値と比べます。マイクロダックは0.16をそのまま宣言しているので、既存の動作は変わりません |

**計画と違っていたこと。** スプリングとコンベヤーは重さと無関係です。`kick`は`qvel`を、`shift`は
`qpos`を直接書きます(`bodies/base.py`)。質量が式に入りません。測定でも確かめました — Go2は
1.5 m/sのキックで0.358 → 0.470 mまで浮いて5/5転ばず、3 s後も歩いていました(2.25 m)。
コンベヤーは3 sで0.85–0.90 mをそのまま運びました(指令0のときのその場の前進0.26–0.35 mを引いた値)。
ロープの結び目の`max_hold_force` 3 Nはくちばしに結ぶ値なので、`grab`の無い体ではそもそも
拒否されます。

## 6. 寸法で解決すること (R47へ送り)

宣言の問題ではなく、**部屋の数値**が一つの体の大きさに合わせられているものです。スキーマの範囲は
余裕があるので、Go2用の部屋プリセットで大きくすればよいです。

| 部品 | 既定値 | Go2の測定 |
|---|---|---|
| `door`/`swing_door`/`rope_door` `width` | 0.5 m | 開いた0.5 mの隙間を5/5通過、0.7・0.9も同じ。ドアの隙間の中での体の最大y幅は0.273–0.288 m(両側に約0.10 mの余裕)。閉じたままの対照群は0/5通過 |
| `pit` `size` | 0.3 m | 0.3 mでは**落ちません** — 5シードのうち1個だけが渡り、4個は縁で転んで「穴の失敗」ではない普通の転倒で終わります。0.6・0.9 mなら5/5落ちます。境界は0.3–0.6 mの間としか分かりません(その間は測っていません) |
| `goal_net` `height`/`width` | 0.12 / 0.36 m | 胴体の上面が0.41 mなので、既定値では入れません(スキーマの上限は0.5 / 2.0 m) |
| サンプルの部屋の大きさ | 2.4 × 1.8 m | 体の長さが0.70 mなので狭いです。監査用には5.0 × 4.0 mを使いました |
| `footprint_radius` | 0.41 m | 円で包むので長い側(0.70 m)を覆います。経路計画は約0.82 mの隙間を要求しますが、実際には0.5 mを通ります。**わざと保守的にしています**: 小さく取ると、体が入らない隙間に経路を引いてしまいます |

## 7. まだ開いていること

- **環境は能力を検査しません。** `mode: grab`のレバーがある部屋も`body: go2`で作られ、リセット
  されます。捕まえるのは`mpg check`だけです。検査を飛ばした利用者は、黙って解けない部屋を
  手にします。
- **目の無い体。** `gaze`・`camera`の観測項目は`view_frame`/`view_camera`を使い、それが無い体では
  それぞれ`NotImplementedError`と`ObsParamError`で落ちます。派手に落ちはしますが、部品の宣言の
  ように`mpg check`が前もって述べてはくれません。
- **「duck」と書いたコメント。** `parts/`の中には、体が一つであることを前提にした散文がまだ
  多くあります(`breakable.py`、`wire.py`、`relay.py`、`brake.py`など)。
  `tests/test_boundary.py`の禁止の一覧は具体的な名前(`microduck`、`go2`、…)しか見ないので、
  この散文は通ります。間違った説明ではありませんが、一つの体を基準に読まれます。
- **`pit`の境界**は0.3–0.6 mの間としか分かりません。使うことになれば、もっと狭める必要があります。
- **ボール押しの操舵は大きな体で測っていません。** 歩きの操舵は、体が`stand_to_turn_above`を宣言すればその場で
  回りますが(R47)、ボールを押す側(`push`)はその宣言を読まず、状況によって指令範囲の中間で回ります。
  旋回半径の大きい体では、それがボールを置いて大きく回る動きになります。`ball`は歩きだけを
  求めるので大きな体もその部屋を受け取りますが、大きな体でボールを押す部屋を測ったことはありません。

## 8. 資産の出どころとライセンス

体ごとにモデルとポリシーを固定リビジョンにピン留めします(`mpg fetch-assets --body <体>`がファイル
ごとのSHA256を確認します)。lockファイルは体ごとに別です。

以下のライセンスは、lockファイルの`license`項目をそのまま写したものです。一つのリポジトリの中でも
ファイルの種類ごとに違うので、まとめて書きません。

| | マイクロダック | Go2 |
|---|---|---|
| モデル | [pollen-robotics/microduck_rl](https://github.com/pollen-robotics/microduck_rl) `0daab16` | [google-deepmind/mujoco_menagerie](https://github.com/google-deepmind/mujoco_menagerie) `370c439`の`unitree_go2/` |
| メッシュ | **CC BY-NC-SA 4.0**(非商用) — `*.stl` | BSD-3-Clause |
| MJCF | Apache-2.0 | BSD-3-Clause |
| 歩行ポリシー | Hugging Face `pollen-robotics/microduck-policies` `283771b`の`velstand.onnx` | Hugging Face `diasAiMaster/unitree-go2-velocity-flat` `9a723b7`の`policy.onnx` + `policy.onnx.data` |
| ポリシーのライセンス | Apache-2.0 | BSD-3-Clause |
| lockファイル | `upstream.lock.json` | `upstream.go2.lock.json` |

**Go2の歩行ポリシーはUnitreeの公式な配布ではありません。** コミュニティが上げたチェックポイントです。
Unitreeが公開したのは学習コード(`unitree_rl_gym`、`unitree_rl_mjlab`)で、凍結された歩行のONNXは
2026-11-15の調査では見つかりませんでした。そのため、このチェックポイントを使うことにしました
(利用者の決定、2026-11-15)。

そのポリシーについて確認した事実です。すべてモデルカードとピン留めしたファイルから読んだものです。

- **平地で学習**しています(課題名`Mjlab-Velocity-Flat-Unitree-Go2`)。階段・斜面は学習の分布の外です。
- `gait_phase`の観測**なし**で学習しており、action scaleは**0.5**です。
- 学習コードはアップストリームの`unitree_rl_mjlab`を**変えていません**(リポジトリに一緒に上げられたdiffが空のdiff)。
- モデルカードが「アップストリームの既定の`deploy.yaml`とは違う場合があるので、このリポジトリの
  `params/deploy.yaml`を使うこと」と書いているので、そのファイルも一緒にピン留めし、アダプターが
  そこから数値を読みます。同じ数値をコードに二度書きません。

マイクロダック側で**非商用**なのはメッシュ(`*.stl`)です。MJCFとポリシーはApache-2.0です。メッシュ
なしではその体をシミュレートできないので、商用で使うならその体そのものを使えないと見るべきです。
Go2側はモデルとポリシーがどちらもBSD-3-Clauseです。

## 9. 歩かない体 (固定ベースのアーム)

三つめの体は歩きません。卓上にボルトで固定されたアームで、**グリッパーがそのまま体**です。パズル側の
コードが体に問うのは四つだけ — 平面上の位置、向き、速度、転んだかどうか — で、計画は2次元の格子で
行います。卓上の操作も平面の問題なので、その四つを**胴体ではなくグリッパーについて**答えれば、同じ
境界がそのまま使えます。`BodyAdapter`は一行も変わっていません。

| | 値 | どうやって分かったか |
|---|---|---|
| 到達半径 | 0.001–0.480 m | 関節の9⁴の格子6,561点を`mj_kinematics`でなぞりました。公開された公式の数値はありません |
| 到達高さ（運動学） | z −0.223 … 0.520 m | 同じなぞり |
| 到達高さ（**制御**） | z 0.111–0.122 m | 各指令上限で4秒ずつ駆動して測定。共通指令 `(vx, vy, wz)` に垂直軸はなく、`step` がグリッパを `WORK_Z` 0.12 m に保持します。よって能力値 `reach_height` は **0.12** です。最初に宣言した0.45は運動学の数値で、0.40 m の壁ボタンを通してしまうところでした |
| 作業帯 | z 0.02–0.15 mで半径0.480 mまで | 同じなぞり |
| 包絡線の形 | 220°の**扇形**(肩の回転±1.920 rad) | 輪ではなく扇形です。部屋がその中に収まる必要があります |
| 自由度 | アーム5軸 + あご1軸、自由関節なし | `nq = nv = 6` |
| 質量 | 0.645 kg | モデルの`body_subtreemass` |
| グリッパーの追従 | 中間の半径で10 cmの移動に約1 cmの誤差 | 指令を2秒与えて測りました。ベース側へ折りたたむと5 cmまで大きくなります |

**宣言した到達半径は `mpg check` が使います**（R77）。基部が動かない体（`reach_max` を宣言し
`walk` を宣言しない体）では、部屋の `demo:` が自分で触ると書いた部品すべてが基部まわりのリング
内にある必要があります。外にあると `body` ステージが距離と範囲を示して拒否します:
`the solution touches 'goal' at 0.6 m from the body's base, outside its reach [0.0, 0.48] m`。
以前は `reach_max`・`reach_min` をどのコードも読んでおらず、目標を 0.6 m に置いた部屋が静的
ステージをすべて通過し、解答でのみ失敗していました。「解答が目標に届かなかった」という
メッセージは、そもそも届き得なかったことを伝えません。

`demo:` が名前を書いていない部品は検査しません。`tabletop/pick_and_place` の扉は基部から
0.72 m、包絡の外ですが、その部屋は 20/20 で解けます。扉は手ではなく信号で開くからです。全部品を
検査するステージは**実際に解ける部屋を拒否**します。なお**扇形はまだ検査しません**: リング内でも
基部の後ろ（死角）にある部品はこのステージを通過します。それを宣言する体がまだないためです。

この体が違うふるまいをする四つのことは、隠さずに表に出します。

- **ベースが固定です。** 自由関節が無いので、`reset`は体を部屋の出発位置へ動かせません — ホームの
  関節角だけを戻し、ベースは`spawn`が置いた場所に残ります。そのため、出発位置をランダムに引く部屋は
  この体には何もランダム化せず、アダプターの`check_warnings`がそう述べます。
- **転びません。** `fallen`はつねに偽で、傾きはつねに垂直なので、`fall`の報酬と終了はこの体では
  永遠に発動しません(taskで切るのが正直です)。
- **歩きません。** `walk`を宣言しないので、歩きを求める部品15個が**名前を述べて**自分から拒否され
  ます。サンプルの部屋をこの体で点検すると`part 'switch_a' needs body capabilities ['walk']`が
  出ます — 黙って解けない部屋にはなりません。
- **向きを命令できません。** 測ってみると、グリッパーの方位角を変える関節は肩の回転だけで
  (+0.2 radで方位角は−0.200 rad、他の関節はすべて0.000)、その関節がグリッパーの**位置**も決めます。
  つまりグリッパーはつねにベースから外を向いています。「振り向いて前進」する操舵では半径の方向にしか
  進めないので、この体は`holonomic`を宣言し、共用の操舵が**向きで**運転します。横方向の指令は直線では
  なく、ベースのまわりの接線の弧を描きます(2秒・0.1 m/sで半径は保たれ、弧は0.2 m)。

**`grab`を宣言しますが、その名前は間違っています。** ゲートが問うのは「自分の末端で物をつかめ
るか」で、このアームはつかめます。名前が最初の体の解剖学から来ているだけで、それはR2が防ごうとして
いる漏れと同じ種類です。`grab`に変えて`grab`を別名として残すのがM4 R60の仕事です。

資産: Menagerieの`robotstudio_so101/`(Apache-2.0)で、このリポジトリが**すでにピン留めしている
コミット**`370c4396`の中にあります。使えるライセンスの事前学習済みポリシーが無いため、制御は逆運動学
です(減衰最小二乗)。キャッシュの経路は`arm/`です — 同じコミットを使う四足の体と`robot/`を共有すると
互いのファイルを上書きします(一度実際にそうなり、`tests/test_assets.py`が今はその衝突を拒否します)。

## 10. ヒューマノイド (Unitree G1)

四つめの体は二本足で歩く29軸のヒューマノイドです。構造は四足の体と同じです — ピン留めしたMJCF、
速度指令`(vx, vy, wz)`を受ける**凍結ポリシー**、平面の指令が入って`BodyState`が出てきます。違う点の
三つは、隠さずにコードに書いておきました。

| | 値 | どうやって分かったか |
|---|---|---|
| 質量 | 33.34 kg | モデルの`body_subtreemass`(メーカーの公開値の約35 kgと一致) |
| 立つ高さ | ペルビス0.79 m | モデルのキーフレーム`stand` |
| 足跡の半径 | 0.316 m → **0.32を宣言** | 立った姿勢で、geomの大きさまで含めて最も遠い距離 |
| 歩く速さ | 指令の上限0.6で**0.455 m/s** | 6秒の走行。指令の約3/4に従います |
| 横の速さ | 指令0.3で0.211 m/s | 同じ方法。転びません |
| その場の回転 | 指令0.5で**0.44 rad/s**(移動0.096 m) | 同じ方法 |
| 旋回の弧 | 指令の中間で0.34 m、上限で1.03 m | 速度 ÷ 回転率。中間が小さいので`stand_to_turn_above`は無限(既定)のままにします |
| `fall_height` | **0.45 m** | 歩いている最中の横のキック: 1.0 m/sは耐え(最低0.722 → 0.766に復帰)、2.0 m/sは転倒(0.058–0.118、体座標の重力+0.18) |
| 20秒の走行 | 6.21 m、転倒なし | 指令0.4 |

**ポリシーは脚の12軸用で、モデルは29軸です。** アップストリームの観測が`obs[9:21] = d.qpos[7:]`に
12個を入れるので、そのロボットの関節はちょうど12個 — 脚だけのモデルです。この体は29軸のモデルの
**脚の12軸**をポリシーに与え、腰と両腕はモデル自身の立つ姿勢で固定します。ポリシーは腕を見たことが
ないので、それでも歩くのかは**仮定ではなく測定**であり、上の表がその測定です。

**観測に歩行の時計が入っています。** 47個のうち最後の二つが、周期0.8秒の位相のsin・cosです。四足の
体のポリシーは位相なしで学習されているので、このアダプターはアップストリームと同じように、時計を
シミュレーション時間で回します。

**チェックポイントはONNXではなくTorchScriptです。** `torch.jit.load`で読みます。

**既存の大きな体の部屋をそのまま解きます。** `puzzles/wide/switch_door`は20/20(平均18.29 s)、
`puzzles/wide/pit_detour`は20/20(平均19.62 s)、どちらも転倒0で、**エピソード長も既定の40秒のまま**
です。部屋は足跡の半径0.41 mの体に合わせて取ってあり、この体は0.32 mなので、すべての隙間がすでに
合っています。速さが四足の体の45 %なのに平均時間が短いのは、この体が大きく回らず、**横に歩いて**
行くからです。

その結論にたどり着く前に、自分のバグを二つ通りました。どちらも「一つの体を前提にしたコード」では
なく、**自分が新しく書いた**ものです。① `action[0] = -1`を既定の線形の対応のままにしたため全速の
**後進**になり、解答の「前が壁ならその場で回転」の値が体を13秒のあいだ後ろへ歩かせ、部屋を出て
転びました(5/5)。リポジトリの規約どおり`command_from_action`を再定義しました(四足の体がR44で同じ
理由でしたのと同じです)。② 上体を「ポリシーが使わないすべてのアクチュエーター」として計算したの
ですが、それは**場面の全体**だったので、この体が毎ステップ、部屋のドアのアクチュエーターを自分の
姿勢で上書きしていました。押されたボタンにつながったドアが最後まで閉じたままでした。今は自分の
接頭辞が付いたアクチュエーターだけに触り、その事実をテストが守ります。

資産: モデルはMenagerieの`unitree_g1/`(BSD-3-Clause)で、このリポジトリが**すでにピン留めしている
コミット**`370c4396`の中にあります。ポリシーは`unitreerobotics/unitree_rl_gym`の
`deploy/pre_train/g1/motion.pt`(BSD-3-Clause、145,745 B)です。**このポリシーもUnitreeが凍結した
公式な配布ではありません** — あのリポジトリが配布の例と一緒に上げておいたチェックポイントです。
キャッシュの経路は`humanoid/`で、観測の順序はピン留めしたコミットの
`deploy/deploy_mujoco/deploy_mujoco.py`から写しました。数値(gain、既定の姿勢、scale)は
`policies/g1.yaml`から読み、コードに二度書きません。

### 手は測って、載せませんでした (2026-11-17)

この体の手は M4 以降ずっと「次の作業」でした。資産は本物で、ポリシーは関節が増えること自体には
耐えます。耐えられないのは、その手を**使えという要求**です。

| 何を | 測定値 |
|---|---|
| 手のモデル | ピン留めしたコミット 370c4396 の `unitree_g1/g1_with_hands.xml`、34,372 B、sha256 `a6d88c9efde50e9715c71e590ce1a8d3515a0099df7f36e62add8204dae758ad`。参照メッシュ49個は**すべて既に lock にありました** |
| 規模 | アクチュエータ43個（29 + 片手7）、nq 50、質量 34.39 kg（手なしで 33.34） |
| 歩行（腕はモデル既定の姿勢） | 指令0.3で 0.218 m/s（手なし 0.227）、上限で 0.445（0.454）、転倒0、骨盤高さ同じ |
| 腕を下げたときの把持点 | 骨盤の**右 0.238 m**、前方 +0.005 m、高さ 0.561 m。歩行中も 0.535–0.576 で安定 |
| 片腕を上げて歩行 | 指令0.3で 0.338 m/s、10秒でヨー +16.1° のドリフト（素の体 0.227・−12.9°） |
| 両腕を上げて歩行 | 指令0.3で **0.832 m/s** — 指令が速度を決めなくなります |
| 両腕を上げて静止 | 指令0なのに6秒で **3.655 m** 歩き去ります |
| 片腕を上げて静止 | 6秒で 0.378 m ドリフト（腕を下げれば 0.187）、転倒なし。把持点は前方 0.429 m・高さ 0.750 m |
| 姿勢12通りの走査（肩ピッチ × 肘） | **すべて**速度追従が崩れました: 指令0.3で 0.36–0.83 m/s、ドリフト +10°〜+52°、1つは転倒 |
| 腰の高さの把持点で固定点を通過（2 m 接近） | 最接近でも **0.448 m** — 把持半径 0.04 m の11倍 |

**理由はポリシーの観測にあります。** ピン留めしたチェックポイントは脚専用で、47個の観測は脚12軸の
角度・速度・前回行動、基部の角速度、重力、指令、歩容位相だけで、**腕が入っていません**。だから腕の
姿勢が重心を動かしても、ポリシーは原因を見られず補正しません。傾き、歩容は指令から離れて走り
出します。測定された歩容をそのまま保つ腕の姿勢は**学習時のその姿勢だけ**で、その姿勢は手を腰の
横に下げます。

**だから把持する体としては載せられません。** 共通の搬送側は体の**中心**を物体に向けます。これまで
把持する体は把持点が中心線の前にあったからです（くちばし、そして体全体がジョーのアーム）。横に
0.24 m 外れた把持点は、中心を狙っても 0.04 m 内には入りません。測定がそう言っています（最接近
0.448 m）。できないことを能力として宣言するのは R67 が禁じた装飾です。

**必要なものを正直な順に。** ① 腕を観測に入れて学習したポリシー — このモデル向けに公開された
ものはありません。② 腕の逆運動学と全身バランス制御 — マイルストーンではなくプロジェクトです。
③ 搬送側が体の中心ではなく**把持点**を狙うようにする — 最初の体の接近精度も上がる最小の変更です
が、それだけでは 0.19 m の静止時の揺れを 0.04 m の半径で乗り越える腰高の把持が残ります。

この試みからは何も載せていません。アダプタも体の登録もなく、手のモデルは再びピンを外しました。
パッケージが読まないファイルを lock が持たないようにするためです。上の数値が記録なので、次の試みは
ダウンロードからではなくこの表から始まります。
